# ADR 0006 — Claude auth: `claude auth login`, credentials on RW PVC, bootstrap via Job

## Status

Proposed — 2026-06-30

## Context

The Claude runtime runs on the OAuth subscription (ADR 0005). We must **connect** this runtime to the
subscription and **maintain** that connection over time, without depending on a mode that leaves the
subscription.

Two technical facts constrain us:

1. Claude Code's OAuth auth **refreshes itself**: `~/.claude/.credentials.json` holds an access +
   refresh token, and the CLI **rotates** them as needed.
2. The **initial login is interactive**: authorize in a browser + retrieve a code ("paste-code"). Not
   bypassable without `setup-token` (a static long-lived token — ruled out: grey zone, and it does not
   refresh correctly).

## Decision

**Auth = `claude auth login`; credentials on a read-write PVC; bootstrap via a one-shot Job.**

- **`claude auth login`** (the real OAuth login, firstParty) — not `setup-token` (static/grey), not an
  API key.
- **The credentials live on the RW PVC** (`~/.claude/.credentials.json`, mounted — ADR 0004). claude
  **rewrites the refreshed credentials** there → auth **self-maintains**. **Definitely not SOPS**: the
  credentials **rotate**, a static copy would go stale then expired.
- **Bootstrap = a one-shot Job** (mounting the PVC) running the login cleanly: it surfaces the
  authorization URL, takes the code, writes the initial credentials to the PVC. **Re-runnable** if it
  expires. This is the *clean and defined* version of the flow — **not** the MVP's exec + FIFO +
  paste-code.
- It is **a human gesture, once per credential** (the interactive part of OAuth is incompressible).

## Rationale

- **Why `auth login` (not `setup-token`/API)** — it is the subscription path that self-refreshes;
  `setup-token` = static + grey zone (same category as SDK/`-p`, ADR 0005); API = per-token cost.
- **Why RW PVC (not SOPS)** — the credentials are **not** a static secret: they rotate. Their right
  home = storage the process can **rewrite** (PVC). SOPS stays for genuinely static secrets (elsewhere).
- **Why a Job (not exec)** — the interactive part is unavoidable, but it deserves a **defined and
  re-runnable flow** (a Job that mounts the PVC, shows the URL, takes the code), not a one-off exec/FIFO
  hack.

## Consequences

- The runtime assumes a **RW PVC** mounted on `~/.claude`; without valid credentials it **does not
  start** → the **bootstrap Job** must have run once.
- The **bootstrap is a documented, re-runnable operational prerequisite** (expired credentials / new
  credential → re-run the Job).
- **Eventually (out of scope here)**: integrate this flow into the **website/admin** ("connect a
  runtime") for a real UX — instead of a hand-launched Job.
- **⚠️ Multi-process / multi-conv — main open risk**: N claude processes in the **same pod** share
  **the same** `~/.claude/.credentials.json`. If Anthropic's OAuth **rotates the refresh-token**, two
  concurrent refreshes can invalidate each other. **To verify**; otherwise plan a strategy (one
  credential per process, or serialize the refresh).
- The exact UX of the Job (how it surfaces the URL + receives the code — logs? a small page?) =
  implementation detail, to settle while building it.
