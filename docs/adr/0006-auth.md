# ADR 0006 — Auth Claude : `claude auth login`, creds sur PVC RW, bootstrap par Job

## Status

Proposed — 2026-06-30

## Context

Le runtime Claude tourne sur l'abonnement OAuth (ADR 0005). Il faut **connecter** ce runtime à
l'abonnement et **maintenir** cette connexion dans le temps, sans dépendre d'un mode qui quitte le
forfait.

Deux faits techniques contraignent :

1. L'auth OAuth de Claude Code **se rafraîchit toute seule** : `~/.claude/.credentials.json` contient
   access + refresh token, et le CLI les **rotate** au besoin.
2. Le **login initial est interactif** : autoriser dans un navigateur + récupérer un code
   (« paste-code »). Non contournable sans `setup-token` (token long-vivant statique — écarté : zone
   grise, et ne se refresh pas correctement).

## Decision

**Auth = `claude auth login` ; creds sur un PVC read-write ; bootstrap par un Job one-shot.**

- **`claude auth login`** (le vrai login OAuth, firstParty) — pas `setup-token` (statique/gris), pas
  de clé API.
- **Les creds vivent sur le PVC RW** (`~/.claude/.credentials.json`, monté — ADR 0004). claude y
  **réécrit les creds rafraîchies** → l'auth **s'auto-maintient**. **Surtout pas SOPS** : les creds
  **rotent**, une copie statique deviendrait stale puis expirée.
- **Bootstrap = un Job one-shot** (qui monte le PVC) déroulant le login proprement : il surface l'URL
  d'autorisation, prend le code, écrit les creds initiales sur le PVC. **Re-jouable** si ça expire.
  C'est la version *propre et définie* du flux — **pas** l'exec + FIFO + paste-code du MVP.
- C'est **un geste humain, une fois par credential** (la part interactive de l'OAuth est
  incompressible).

## Rationale

- **Pourquoi `auth login` (pas `setup-token`/API)** — c'est le chemin abonnement qui s'auto-refresh ;
  `setup-token` = statique + zone grise (même catégorie que SDK/`-p`, ADR 0005) ; API = coût au token.
- **Pourquoi PVC RW (pas SOPS)** — les creds ne sont **pas** un secret statique : elles rotent. Leur
  bon foyer = un stockage que le process peut **réécrire** (PVC). SOPS reste pour les secrets
  réellement statiques (ailleurs).
- **Pourquoi un Job (pas l'exec)** — la part interactive est inévitable, mais elle mérite un **flux
  défini et re-jouable** (un Job qui monte le PVC, montre l'URL, prend le code), pas un bricolage
  exec/FIFO one-off.

## Consequences

- Le runtime suppose un **PVC RW** monté sur `~/.claude` ; sans creds valides il **ne démarre pas** →
  le **Job de bootstrap** doit avoir tourné une fois.
- Le **bootstrap est un prérequis opérationnel** documenté et re-jouable (creds expirées / nouveau
  credential → re-run le Job).
- **À terme (hors scope ici)** : intégrer ce flux dans le **website/admin** (« connecter un
  runtime ») pour une vraie UX — au lieu d'un Job lancé à la main.
- **⚠️ Multi-process / multi-conv — principal risque ouvert** : N process claude dans le **même pod**
  partagent **le même** `~/.claude/.credentials.json`. Si l'OAuth Anthropic **rotate le refresh-token**,
  deux refresh concurrents peuvent s'invalider mutuellement. **À vérifier** ; sinon prévoir une
  stratégie (un credential par process, ou sérialiser le refresh).
- L'UX exacte du Job (comment il surface l'URL + reçoit le code — logs ? petite page ?) = détail
  d'implémentation, à fixer en le construisant.
